# Веб-хаб для студентов группы 8К64 ТПУ

Веб-хаб создан для студентов группы **8К64 Томского политехнического университета (ТПУ)**. Его цель — собрать полезные учебные сервисы и информацию о занятиях в одном месте.

## Возможности проекта

- **Главная страница** со ссылками на сервисы ТПУ.
- **Расписание группы** из ro-rasp с фильтром по подгруппам 1 и 2.
- **Карточки занятий** со ссылками на соответствующий курс Moodle и страницу преподавателя.
- **Заметки к парам**: сохраняются в браузере с помощью `localStorage` и **не отправляются на сервер**. Заметки доступны в том браузере и на том устройстве, где они были созданы.

## 📂 Структура проекта

Ниже приведено краткое описание основных файлов и каталогов репозитория:

- `index.html` — главная страница веб-хаба: HTML-разметка, метатеги и настройки отображения на мобильных устройствах.
- `css/` — каталог таблиц стилей.
  - `style.css` — основные стили проекта.
- `js/` — JavaScript-код, отвечающий за интерактивность и логику клиентской части.
- `images/` — изображения, логотипы и иконки.
- `data/` — данные проекта в формате JSON.
- `scripts/` — вспомогательные Python-скрипты, например для обработки данных или автоматизации задач.

> Структура может дополняться по мере развития проекта. При добавлении новых файлов сохраняйте понятное назначение каталогов.

## Как мы работаем с Git

### 1. Основные правила

- **`main` — стабильная ветка.** Она защищена: прямой `push` в неё запрещён. Изменения попадают в `main` только через Pull Request (PR) с одобрением ревьюера.
- **Одна задача — одна ветка.** Для каждой отдельной задачи создаём свою ветку.
  - `feature/<коротко>` — новая возможность, например `feature/mock-api`, `feature/fetch-weeks`, `feature/home-page`.
  - `fix/<коротко>` — исправление ошибки.
- **Ветки должны жить недолго — обычно 1–5 дней.** Чем дольше ветка существует отдельно от `main`, тем выше вероятность конфликтов при слиянии.
- **Перед созданием PR обновите свою ветку свежим `main`.**
- **Пишите понятные сообщения коммитов на русском языке.** Например: `Добавлен рендер карточек из мока`, `Исправлена дата в заголовке недели`. Неудачные варианты: `правки`, `fix`, `изменения`.
- **Не коммитьте временные и локальные файлы.** В частности, `backend/data/raw/`, `.venv/`, `.vscode/` и `__pycache__/`. Эти пути уже перечислены в `.gitignore`.

### 2. Как обновить свою ветку перед PR

В терминале выполните команды по очереди, заменив `feature/моя-ветка` на имя своей ветки:

```bash
git checkout main
git pull
git checkout feature/моя-ветка
git merge main
```

`git pull` получает актуальное состояние удалённой ветки `main`, а `git merge main` переносит эти изменения в вашу рабочую ветку. Если при слиянии появятся конфликты, сначала разрешите их, затем завершите слияние.

## Полный цикл задачи

### 1. Создайте новую ветку

Начинайте работу с актуального `main`:

```bash
git checkout main
git pull
git checkout -b feature/имя-задачи
```

Для исправления ошибки вместо `feature/` используйте `fix/`, например `fix/week-date`.

### 2. Внесите изменения и создайте коммит

После работы проверьте изменения и добавьте нужные файлы:

```bash
git add .
git commit -m "Кратко описано, что сделано"
```

- `git status` показывает изменённые файлы и текущее состояние рабочей копии.
- `git add .` добавляет изменения из текущего каталога в индекс для следующего коммита. Перед выполнением проверьте, что в список не попали лишние файлы.
- `git commit -m "..."` сохраняет подготовленные изменения в истории текущей ветки.

### 3. Отправьте ветку на GitHub

При первой отправке новой ветки выполните:

```bash
git push -u origin feature/имя-задачи
```

Команда отправляет ветку в удалённый репозиторий GitHub и связывает её с локальной веткой. Для последующих отправок из этой ветки обычно достаточно `git push`.

### 4. Создайте и завершите Pull Request

1. Откройте репозиторий на GitHub и нажмите **Compare & pull request**.
2. Заполните описание PR по шаблону, укажите связанную задачу и шаги проверки.
3. Назначьте ревьюера и дождитесь одобрения.
4. После одобрения **автор PR самостоятельно нажимает `Merge`**.
5. После успешного слияния удалите удалённую ветку кнопкой **Delete branch**.

Затем обновите локальный `main`:

```bash
git checkout main
git pull
```

После этого можно начинать следующую задачу с новой ветки.

### Кратко о командах

| Команда | Назначение |
| --- | --- |
| `git checkout main` | Переключает на локальную ветку `main`. |
| `git pull` | Получает изменения из связанной удалённой ветки и обновляет локальную ветку. |
| `git checkout -b feature/имя-задачи` | Создаёт новую ветку и сразу переключает на неё. |
| `git add .` | Добавляет изменения из текущего каталога в индекс для коммита. |
| `git commit -m "Сообщение"` | Сохраняет подготовленные изменения в локальной истории Git. |
| `git push -u origin feature/имя-задачи` | Отправляет ветку на GitHub и настраивает связь с удалённой веткой. |
| `git merge main` | Вливает изменения из локальной ветки `main` в текущую ветку. |

## Как оформлять Pull Request

Pull Request (PR) — это запрос на включение изменений из вашей ветки в `main`. Он нужен, чтобы команда могла проверить код до слияния.

- **Название должно описывать результат.** Например: `Добавлена фильтрация расписания по подгруппам`.
- **В описании укажите связанную задачу.** Используйте ключевое слово, например `Closes #13`, а также кратко опишите изменения и способ их проверки.
- **Для фронтенда добавляйте скриншоты** на двух размерах: телефон (ширина 360 px) и десктоп (ширина 1200 px).
- **Один PR — одна задача.** Если изменения в PR превышают примерно 300 строк, проверьте, можно ли разделить работу на несколько небольших PR.
- **Ревьюер — DevOps/QA.** Если меняется формат данных или контракт между частями проекта, дополнительно подключите к ревью куратора.
- **Сливает PR его автор**, но только после необходимого одобрения.

В репозитории есть шаблон `.github/pull_request_template.md`: GitHub автоматически подставляет его в описание нового PR. Заполните все подходящие разделы и отметьте пункты чек-листа.

### Как работает `Closes #N`

Запись `Closes #13` должна находиться **в описании PR**, а не только в названии. Когда PR с таким описанием будет слит в `main`, GitHub автоматически закроет issue № 13.

Если PR закрывает несколько задач, укажите каждую отдельно, например:

```text
Closes #6
Closes #7
```

## Если что-то пошло не так

### Случайный коммит в локальный `main`

Если вы случайно сделали коммиты прямо в локальной ветке `main`, не пытайтесь отправлять их напрямую: защищённая ветка отклонит `push`. Создайте рабочую ветку на основе текущего состояния `main` — ваши коммиты останутся в ней:

```bash
git checkout -b feature/имя-задачи
git push -u origin feature/имя-задачи
```

Затем откройте PR обычным способом. Когда убедитесь, что нужные коммиты сохранены в новой ветке, верните локальный `main` к состоянию удалённой ветки:

```bash
git checkout main
git fetch origin
git reset --hard origin/main
```

> **Осторожно:** `git reset --hard origin/main` удаляет незакоммиченные изменения в текущей ветке и сбрасывает её указатель на `origin/main`. Перед выполнением убедитесь, что все нужные коммиты находятся в новой ветке, а незакоммиченные изменения сохранены или больше не нужны.

### Конфликт при `git merge main`

VS Code подсветит конфликтные участки и предложит варианты **Accept Current**, **Accept Incoming** или **Accept Both**. Проверьте результат вручную: не выбирайте вариант автоматически, если не уверены, какой код нужен.

После разрешения конфликтов выполните:

```bash
git add .
git commit -m "Разрешены конфликты с main"
```

Если непонятно, какую версию оставить, свяжитесь в командном чате с автором второго изменения и согласуйте решение.

## 🚀 Как запустить проект локально

Локальный запуск позволяет проверить страницу в браузере до создания Pull Request.

### Способ 1. Расширение Live Server в VS Code (рекомендуется)

1. Откройте папку репозитория в **VS Code**.
2. При необходимости установите расширение **Live Server**.
3. Нажмите правой кнопкой мыши на `index.html` и выберите **Open with Live Server**. Также можно нажать **Go Live** в правом нижнем углу окна редактора.
4. Проект откроется в браузере.

### Способ 2. Встроенный HTTP-сервер Python

Если Python установлен, откройте терминал в корневой папке репозитория и выполните:

```bash
python -m http.server 8000
```

На macOS или Linux может потребоваться команда `python3 -m http.server 8000`.

После запуска откройте в браузере адрес [http://localhost:8000](http://localhost:8000).
